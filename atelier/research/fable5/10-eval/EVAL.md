# EVAL.md — Atelier Helix qualitative evaluation

Fable5#10. This document defines the qualitative evaluation protocol for
Atelier Helix (brief→plan quality, routing correctness, canvas pin) and
records the results of running it against the fleet's actual deliverables on
2026-08-21. The scorecard is generated by `python3 test_helix.py --eval`, so
it can be re-run at any time against updated components.

## 1. What was evaluated

| concern          | component under test                                     | binding at eval time |
|------------------|----------------------------------------------------------|----------------------|
| store            | `04-helix-arch/schema.sql` (Helix memory schema)         | real                 |
| conductor parse  | `05-conductor/conductor.py` (`parse_plan`, `parse_critique`, `order_steps`) | real |
| routing          | `05-conductor/conductor.py` (`route_plan`, ROUTING.md rules) | real            |
| usage ledger     | `08-security-quota/usage.py` (`UsageLedger`, `BudgetGuard`) | real              |
| media loom demo  | `07-loom/loom.py` (keyless demo pipelines)               | real                 |
| pipeline demo runs | `helix_ref.py` (scripted spokes driving the staged brief→pin run) | bundled reference |

The bundled reference (`helix_ref.py`) implements the PROTOCOL.md contract
with deterministic spokes so full pipeline runs are testable offline; when a
real end-to-end runner ships, point the loom tests at it and keep the same
assertions. No live API key was present in the environment for any run, and
socket connections were hard-blocked during every demo run
(`forbid_network` monkeypatches `socket.socket.connect`).

## 2. Rubric

Each fixture brief (see `fixtures/`) is scored on five dimensions, 0–2 each,
10 per fixture. 2 = fully meets the bar, 1 = partial, 0 = fails or errors.

| dim | name             | what 2 points requires |
|-----|------------------|-------------------------|
| D1  | task-type fidelity | Every craft the task demands appears in the plan (`crafts_required`), plus at least one supporting craft (`crafts_any_of`). A logo brief must render an image; a brand-kit apply must `refine-image`, not regenerate. |
| D2  | constraint capture | Every palette hex and named entity from the brief is restated inside step instructions or the plan reading — PROTOCOL.md's rule that "constraints must be restated inside every instruction they bind". |
| D3  | routing correctness | Every step bound to a lane; required lanes used; no forbidden lane (`video`/`audio`/`3d`); count of decisions equals count of steps. |
| D4  | plan hygiene     | Step and handoff counts meet the fixture floor; assumptions recorded for underspecified briefs; the plan parsed cleanly (DAG, unique ids/names, acceptance criteria — all enforced by `parse_plan`, so a plan that reaches scoring already passed them). |
| D5  | pin + canvas     | The demo run pins artifacts to disk with a valid `conductor-manifest/1` (sha256 and byte counts match the files); every artifact then registers in the store schema and pins to a board, visible through `v_board_scene`. 1 point manifest, 1 point board. |

## 4. Brief → plan quality (qualitative)

Plans were produced by the deterministic demo planner and validated by the
**real** `parse_plan`. Observations per fixture:

- **logo** — Three steps in the right shape: direction (`compose-text`) →
  mark (`render-image`, consuming the direction via `[[s1]]`) → style note
  (`synthesize`, consuming both). The one-colour constraint `#1A5FB4` is
  restated in the render instruction *and* in its acceptance criterion
  ("uses only #1A5FB4 on white"), which is exactly the self-contained-step
  discipline PROTOCOL.md demands. The "three directions to compare"
  requirement lands in s1's instruction and acceptance. Assumption recorded
  (white background), matching the brief's silence on background.
- **poster** — Copy block is a separate text step ahead of the render, so
  dates/venue survive as text rather than being trusted to pixels; a closing
  `analyze-visual` legibility read operationalises "legible from three
  metres" into a checkable verdict. All three hexes restated.
- **factsheet** — The strongest test of content flow: the three Queensland
  Legal Directory entries enter as structured data, are normalised to a JSON
  content model, and the harness verifies the *artifact bytes* (not the
  prompts) still contain "Basic Rights Queensland", "Gold Coast Community
  Legal Centre" and "1800 012 255" after two `[[token]]` hops. Accessibility
  constraints ("no decorative imagery over text") are restated in both the
  template spec and the render instruction.
- **brand_apply** — The plan correctly reads "apply the kit" as
  audit (`analyze-visual`) → restyle (`refine-image`) → change log
  (`synthesize`), never `render-image`: composition is preserved by craft
  choice, not by prompt hope. Fonts (Archivo/Inter) and all three kit hexes
  are restated in the restyle instruction.

Weaknesses to watch when a live LLM planner replaces the demo planner:
D2 will be the first dimension to degrade (models paraphrase hexes), and
D4's assumption discipline needs the scorecard-flag rule from thinking mode
to be enforced by prompt, not hoped for.

## 5. Routing correctness

Observed lane decisions from the real `route_plan` (rules from ROUTING.md,
first match wins):

| fixture | step / craft | lane | rule exercised |
|---|---|---|---|
| logo | s1 compose-text → `openai`, s2 render-image → `image`, s3 synthesize → `gemini` | | 5, 1, 3 |
| poster | s1 compose-text → `openai`, s2 render-image → `image`, s3 analyze-visual → `gemini` | | 5, 1, 2 |
| factsheet | s1 compose-text → `openai`, s2 synthesize → `openai`, s3 render-image → `image` | | 5, 5, 1 |
| brand_apply | s1 analyze-visual → `gemini`, s2 refine-image → `image`, s3 synthesize → `gemini` | | 2, 1, 3 |

The four fixtures jointly exercise routing rules 1, 2, 3 and 5. Rule 4
(long-source ≥ 8,000 chars → `gemini`) is not covered by a launch fixture;
covered instead by the rule-order unit test structure — a long-brief fixture
is a recommended addition (see §8). Invariants asserted for every step of
every fixture: image-emitting steps ride the `image` lane and only that lane;
`analyze-visual` always gets a multimodal reader; no step is unrouted; no
`video`/`audio`/`3d` lane exists to be misrouted to; a registry missing a
lane fails loudly *before* any step runs.

**Sensitivity check (mutation test):** binding the harness to a deliberately
broken conductor whose `route_plan` sends every step to the `openai` lane
produced 10 failures across the routing tests. The tests are not vacuous.

## 6. Canvas pin

Two layers verified:

1. **Run-directory pin (conductor `pin` stage).** Every artifact is written
   under `<out_dir>/artifacts/` and listed in `manifest.json`
   (`conductor-manifest/1`) with matching sha256 and byte size; handoff
   flags mark the client-facing set; image artifacts are valid PNGs;
   reruns with a fixed run id and clock are byte-identical.
2. **Board pin (store schema).** Manifest artifacts insert as immutable
   `artifacts` rows and pin as `board_nodes` with real geometry; all pins
   surface through `v_board_scene`; invariant I5 rejects an artifact node
   with no artifact; moving a pin is allowed; deleting a pin never deletes
   the artifact behind it (projection semantics confirmed).

## 7. Security posture observed

- Demo mode requires no keys: provider resolution falls back to `demo` when
  no key env vars exist, and demo runs complete with sockets blocked.
- Live providers without keys fail loudly (`MissingKeyError`) *before* any
  network attempt.
- Ledger metadata is scrubbed: OpenAI-style `sk-…`, Google `AIza…` and
  bearer tokens all land as `[REDACTED]`.
- Budgets are pre-call: `BudgetGuard` blocks the daily and per-thread cap
  crossings, and rejects negative projections.
- Video never auto-routes to a paid backend.

## 8. Gaps and recommended follow-ups

1. **Rule 4 fixture** — add a ≥ 8,000-char brief (e.g. the full legal
   directory export) to exercise the long-context lane end to end.
2. **Real end-to-end runner** — these demo runs use the bundled reference
   conductor pipeline with scripted spokes. When `Conductor.run` from
   05-conductor is wired to the 07-loom spokes, run the same DemoLoomTests
   assertions against it (injected clock and `run_id` make it reproducible
   per PROTOCOL.md §5).
3. **Live-model plan quality** — D2/D4 scores here reflect a deterministic
   planner; re-run `--eval` with a real planner spoke and expect degradation.
   The rubric is designed to be stable across that swap.
4. **ΔE brand compliance (ACCEPTANCE.md M-5)** — pixel-level palette checks
   on rendered images are out of scope for placeholder artifacts; add once a
   real image spoke produces full-size renders.
5. **Board UI (06)** — `v_board_scene` is verified at the store layer; DOM
   verification of 06-board-ui is manual for now (see ACCEPTANCE_CHECKLIST.md).
